El proceso, paso a paso

01

Levantar la API objetivo

Antes de escanear algo hace falta que esté corriendo. Se activó el entorno virtual de la Actividad 4 y se generó un token de sesión para el endpoint protegido.

bash
$ cd 04 && source venv/bin/activate
$ export API_TOKEN=$(python -c 'import secrets;print(secrets.token_urlsafe(32))')
$ python app.py &
$ curl http://localhost:5000/health
200 OK API arriba — {"status": "ok"}
02

Preparar OWASP ZAP

Se descargó la imagen oficial de ZAP y se confirmó que el contenedor arranca correctamente antes de lanzar cualquier ataque real.

bash
$ docker pull ghcr.io/zaproxy/zaproxy:stable
$ docker run --rm ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py --help
Listo Imagen descargada · zap-full-scan.py responde

04

Active scan directo sobre cada endpoint

Ya que el spider no puede encontrar rutas de una API sin frontend, se apuntó el escaneo activo directamente a cada endpoint conocido por el código: el público (/health) y el protegido (/usuarios), este último inyectando el token vía el add-on Replacer de ZAP en cada petición.

4a · /health — público

bash
$ docker run --rm --network=host -v "$(pwd)/evidencias:/zap/wrk/:rw" \
    ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
    -t "http://localhost:5000/health" \
    -r zap-reporte-health.html -J zap-reporte-health.json -I

4b · /usuarios?id=1 — protegido, con Bearer token inyectado

bash
$ docker run --rm --network=host -v "$(pwd)/evidencias:/zap/wrk/:rw" \
    ghcr.io/zaproxy/zaproxy:stable zap-full-scan.py \
    -t "http://localhost:5000/usuarios?id=1" \
    -r zap-reporte-usuarios.html -J zap-reporte-usuarios.json -I \
    -z "-config replacer.full_list(0).matchtype=REQ_HEADER …

Mismos hallazgos en ambas fechas — sin regresiones

El código de 04/app.py intenta explícitamente remover el header Server, y tanto Bandit como Semgrep (Actividad 07) habrían dado por buena esa línea — ninguna de las dos ejecuta el código, solo lo leen. Sólo al mandar una petición HTTP real se descubrió que el header seguía presente, porque lo agrega el servidor de desarrollo a nivel de socket, después de que la aplicación ya terminó de correr. Esa es la vulnerabilidad que solo aparece en ejecución.
